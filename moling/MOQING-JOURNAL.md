# 魔卿优化记录

判定以正式宇浩测评为准，看每一轮全部线程，不只看综合得分第一名。目标是知乎字频下简码动态重码率不超过 5%，以及知乎、北语全部简码速度当量不超过 1.29；实际值等于目标也算达标。优先级：先满足两项目标，再在目标不退步的前提下优化全码质量和按键分布。所有测评均按魔卿三码规则：字根双编码，大码与声码均使用排除 `a/e/i/o/z` 后的 21 个字母键，无音声码为 `v`；单根 `A1S1S1`、双根 `A1A2S2`、多根 `A1A2Az`。固定单字简码为 `a/e/i/o`，动态简码为 `A1[aeio]` 和 `A1A2[aeio]`；不启用其它简码级别。

优化入口在 `moling/` 目录执行，`SCHEMA=moqing`。优化过程中只调整 `config-moqing.toml` 和 `key_distribution-moqing.txt`；本记录文件用于记录过程。正式宇浩方案为 `../../yuhao-assess-data/schemes/moqing.json`，最大码长为 3，简码终止键为 `a/e/i/o/_`。最终目标以该正式方案的宇浩测评数字为准。

### 当量瓶颈调查

#### 1. 两套当量公式不完全相同

Code Genie 在 `src/context.rs` 的 `calc_equiv_from_parts` / `calc_simple_equiv` 中，会把最后一个核心键到空格的键对也计入，并用核心码步数作除数。三码全码近似为：

```text
(A1,A2) + (A2,A3) + (A3,空格)，再除以 3
```

宇浩正式测评在 `yuhao-assess/src/services/speedEquivalentService.ts` 的 `从码表计算加权速度当量` 中，只统计实际编码字符串的相邻键对，不额外添加末尾空格；全部简码还会直接使用完整简码/全码表的实际字符串，并按所有相邻键对频率加权平均。因此 Code Genie 的内部全码/简码当量不是正式验收指标的同一个量。

第 8 轮 T3 的 Code Genie 内部全码当量约 `1.2919`、简码内部当量约 `1.0702`，但正式知乎全部简码当量仍为 `1.2926`。内部简码当量很低并不意味着正式“全部简码”会同比下降；两者的码长、末尾空格处理、简码覆盖范围和相邻键对分母都不同。

#### 2. 高当量来自高频字的具体键对路径

`pair_equivalence.txt` 是固定输入，字母键对的成本从约 `1.0` 到 `2.1`；优化只能移动字根键位，不能改变这个矩阵。第 7 轮 T3 的高频全码路径示例：

| 汉字 | 频率加权全码 | 键对成本 | 说明 |
|---|---|---|---|
| 人 | `grr` | `gr=1.8`、`rr=1.3`、内部 `r_ = 1.4` | 高频字根声码集中在 `r`，第一跳很贵 |
| 有 | `pmv` | `pm=1.7`、`mv=1.2`、内部 `v_ = 1.2` | 大码组合 `p→m` 是高成本跨区 |
| 了 | `nll` | `nl=1.5`、`ll=1.4`、内部 `l_ = 1.2` | 同手重复/小跨排组合占高频 |
| 一 | `fuu` | `fu=1.2`、`uu=1.3`、内部 `u_ = 1.3` | 单根三码规则强制重复声码 `S1S1` |
| 我 | `lsm` | `ls=1.1`、`sm=1.1`、内部 `m_ = 1.3` | 末键成本和高频末根分配仍有影响 |

按全码 `output-encode.txt` 的频率分解，内部末尾空格项中 `l/u/m/v/s/j/c/b` 占据大量权重，其中 `s_ = 1.4`、`u_ = 1.3`、`m_ = 1.3`；不计空格的正式相邻键对中，`gr=1.8`、`pm=1.7`、`nl=1.5`、`ll=1.4`、`uu=1.3` 等高频路径仍然占据主要成本。高当量不是一个孤立坏键，而是高频根的多次相邻转移叠加。

#### 3. 字根允许键簇造成结构性限制

`moling/init.sh` 为高频、中频、低频字根设置了不同的大码允许键簇；魔卿还必须在 25 键空间中排除 `a/e/i/o/z`。同时，魔卿是双编码字根，单根字强制 `A1S1S1`，导致同一个声码连续出现；多根字又强制 `A1A2Az`。因此高频根不能任意独立选择两个最优键，且一个根的 A/S 位置会同时影响多个高频字的转移。

#### 4. 键位分布不是定向键对优化器

`key_distribution-moqing.txt` 只对每个键的边际使用率进行惩罚，无法表达“某键只适合放在 A 位、不适合放在 S 位”，也无法直接惩罚 `gr`、`pm`、`nl` 这类有方向的键对。第 7 轮将字母高侧惩罚全部置零后，正式当量从 `1.2978` 改善到 `1.2927`，证明边际分布约束确实曾挡住一部分搜索；但继续放松边际惩罚不能消除上述键对和规则结构的成本。

#### 调查结论与后续杠杆

当前难以降到 `1.27` 的主要原因按重要性排序是：固定 `pair_equivalence.txt` 的高成本键对；魔卿三码规则尤其是 `S1S1` 的重复声码；高频字根允许键簇；Code Genie 内部当量与宇浩正式全部简码当量口径不一致。第 8 轮已显示单纯加步和同盆地增量的收益接近于零。

后续若继续，不应再盲目增加 `total_steps`。应优先做一次可归因的简码分配策略实验（例如 `simple_assign_mode = "frequency"` 与当前 `efficiency` 对比），或者针对外部相邻键对成本重新设计可表达的键位边际目标；每次仍只改一类因素并完整测评。当前两项目标尚未全部达成，未选择最终布局。

## Code Genie 当量代码审计（暂停自动优化）

针对“是否无视最大码长和上屏键集合、总是添加空格”的疑问，检查了 `src/context.rs`、`src/evaluator.rs`、`src/main.rs` 和现有属性测试，结论如下。

### 全码：确认存在无条件空格项

`OptContext::calc_equiv_from_parts` 当前逻辑是：

```rust
for i in 1..n {
    total += equiv_table[prev_key][cur_key];
}
total += equiv_table[prev_key][KEY_SPACE];
total / n as f64
```

也就是说，只要拆分部件数 `n > 0`，不论实际最大码长、不论方案是否配置简码上屏键，都会追加最后一个键到 `KEY_SPACE` 的当量。`annealing.max_parts`/`ctx.max_parts` 没有参与这个判断；它主要用于上下文元数据、桶空间日志和准备阶段的最大码长警告。魔卿的 `MAX_CODE_LEN=3` 只是在 `prepare-inputs.sh` 生成 `input-division.txt` 时截断输入，不能改变该函数无条件追加空格的逻辑。

这与正式宇浩速度当量的口径不一致：宇浩 `speedEquivalentService.ts` 只统计实际码表字符串的相邻键对，不自动添加末尾空格。因此全码内部当量会优化一个额外的、未配置的终止键转移。

### 简码：不是无条件空格，但分母口径有意不同

`OptContext::calc_simple_equiv` 只在 `commit_key: Option<u8>` 为 `Some` 时追加末位转移：

```rust
if let Some(ck) = commit_key {
    total += equiv_table[prev_key][ck as usize];
}
total / n as f64
```

因此：

- 动态简码分到 `e/a/i/o` 时，计入实际分得的那个上屏键，不会自动改成空格；
- 显式空格上屏时，`commit_key` 才是 `KEY_SPACE`；
- 无上屏键级别或没有分配上屏键时，不追加空格；
- 固定简码常量贡献也遵循同样逻辑，只有字面简码显式归属了末位上屏键才计入。

但简码仍使用“核心指令步数 `n`”作分母，而不是实际相邻键对数量：无上屏键的 n 键核心只有 n-1 个转移，却除以 n；有上屏键时有 n 个转移，才正好除以 n。现有 `space_commit` 属性测试明确把这种行为作为设计口径测试，因此这是已固化的内部指标定义，不是偶然分支。

### 结论

用户怀疑的一半是正确的：

1. **全码确实无条件添加空格**，且不看 `max_parts` 或任何上屏键集合；这是与正式速度当量目标不一致的代码逻辑。
2. **简码不是总是添加空格**，它尊重实际 `commit_key`；但它使用核心步数作分母，也没有完全复用正式宇浩的“实际编码字符串相邻键对平均”口径。
3. 当前属性测试验证的是这套旧的内部口径，不代表它与魔卿正式宇浩目标一致。

若要让退火内部当量直接对齐正式目标，建议把全码和简码都改为：构造实际输出键串（全码不自动补空格；简码只在实际有 `commit_key` 时追加），只累加相邻键对，并除以实际相邻键对数量；单键且没有相邻键对时定义为 0 或从当量频率分母排除。对应测试也要从“空格上屏使 n 步当量为 1”的旧断言改为实际键串口径。

本轮只完成审计和记录，没有修改 Rust 源码，也没有继续启动优化。

### 第 25 轮种子覆盖后续审计：确认是后缀回退错误

对第 25 轮种子覆盖警告进一步逐组核查后，确认 11 组如下：`{烏上}.0 {鳥上}.0 烏.0 鳥.0`、`門.0 鬥.0`、`{亜下}.0 {亞下}.0 {亞中}.0`、`冎.0 咼.0`、`{馬上}.0 馬.0`、`貝.0`、`見.0`、`來.0`、`魚.0`、`{爲下}.0`、`頁.0`。它们在种子 `output-keymap.txt` 中都有对应基础根编码，并非种子输出漏行。

这 11 个基础根在优化用的 `input-division.txt`/`chaifen.txt` 中出现次数均为 0，所以 Code Genie 的 8,105 字退火目标没有使用这些组；但它们在完整 `chaifen-all.txt` 中实际出现：合计约 9,929 个含这些根的字符条目，源频率列合计约 72,488。因此它们不影响本轮退火内部得分，却会影响完整 `mabiao.tsv` 的少量全字集编码、静态重码和正式全字集测评的可复现性。

根因是：当前 `input-fixed.txt` 对这些基础根同时定义了 `.0` 受限组和 `.1` 固定映射。例如 `烏.0` 属于动态/受限组，`烏.1` 在另一行固定为 `w`；输出器按基础根合并后写成 `烏\tlw`。但 `src/loader.rs::load_keymap` 只从 `input-division.txt` 推断后缀；基础根不存在时使用默认 `[-1, 1, ...]`，于是把 `lw` 展开成 `烏=l、烏.1=w`，没有生成当前组需要的 `烏.0=l`。`keymap_to_assignment` 随后把该组判为缺失并随机填充。

判定：这不会使退火程序非法或使所有增量优化失效，因为 11 组不在 8,105 字优化语料中；但它破坏了“完整复用种子”的增量语义，并给完整码表和正式测评引入了随机噪声。建议在下一轮前修正 loader：对 `input-division.txt` 未覆盖的基础根，应从当前 `input-fixed.txt` 的 `.0/.1/.2` 子根定义补充后缀顺序（division 优先，fixed 作为缺失基础根的回退），而不是使用 `[-1,1,...]`。修正后应从同一 T3 种子重跑一次校正基线，再继续下一轮；本次第 25 轮结果保留但标记为存在 11 组随机补全，不应作为严格可复现的增量基线。
